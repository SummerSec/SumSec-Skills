# 创建流程详细指南

本文档描述从零创建流程编排 Skill 的五步详细流程。

---

## Step A: 需求梳理与步骤分解

与用户确认以下信息，补齐缺口：

### A.0 收集具体示例（先行）

在讨论任何结构之前，先收集 2-3 个真实的用户原句：

1. 用户会怎么描述需求？（记录原句，保留口语化表达和缩写）
2. 输入的典型形式是什么？（URL？文件路径？参数名？）
3. 期望的输出是什么？（具体格式、文件类型、包含字段）
4. 哪些说法应该触发这个 skill？（正式说法 + 口语说法 + 简写）

**为什么这一步重要**：description 的触发短语和 skill 的输入门槛设计，直接来源于这些真实原句。跳过这一步会导致 skill 设计精美但无人触发或参数收集不全。

### A.1 任务画像

1. 这个 skill 要解决什么问题？（一句话）
2. 输入是什么？（用户提供什么信息）
3. 最终输出是什么？（报告？JSON？文件？）
4. 输入是否总是由用户一次性提供，还是需要多轮交互收集？

### A.2 步骤分解

1. 将任务分解为 3-8 个顺序步骤
2. 每步有清晰的一句话说清目标
3. 步骤之间有明确的前置依赖关系
4. 标注哪些步骤需要读取外部参考文件，哪些只需要进度文件

### A.3 状态识别

1. 哪些信息需要在步骤之间传递？（中间分析结果、路径、配置等）
2. 哪些信息是每步独立计算的？
3. 是否需要跨步骤累积列表或表格数据？

## Step B: 目录结构设计

基于 A 的分析结果，设计 Skill 目录结构。使用脚手架脚本快速生成：

```bash
python3 ~/.claude/skills/workflow-skill-creator/scripts/scaffold_workflow_skill.py \
  --name {skill-name} \
  --steps {n} \
  --step-names "步骤1名,步骤2名,..." \
  --output ~/.claude/skills/{skill-name}/
```

**生成的标准目录结构**：

```
{skill-name}/
├── SKILL.md                          # 主文件：概览 + 步骤概要 + 资源索引
├── references/
│   ├── step_frameworks/              # 每个 Step 的详细框架（核心）
│   │   ├── step1_xxx.md
│   │   ├── step2_xxx.md
│   │   └── ...
│   ├── progress_file_spec.md         # 进度文件规范
│   ├── domain_knowledge.md           # 领域知识/规则定义
│   ├── judgment_rules.md             # 判定规则（如有）
│   └── data_source.csv               # 权威数据源（如有）
├── scripts/                          # 确定性任务脚本
│   └── path_generator.py             # 至少包含路径生成脚本
└── assets/                           # 输出模板
    ├── progress_template.md          # 进度文件模板
    └── output_template.md            # 最终输出模板
```

## Step C: 撰写 SKILL.md

SKILL.md 遵循 `assets/skill_template.md` 的结构。

### C.1 Frontmatter

- `name`: kebab-case
- `description`: 触发条件先行，包含 what + when + 中文触发关键词

**好的 description 示例**：
```yaml
description: 当用户要求创建流程编排类 Skill、管线 Skill、工作流 Skill，或提及流程编排、pipeline skill、步骤框架、进度文件、任务编排时，应使用此技能。提取自 biz-vul-security 的六大架构模式。
```

### C.2 主体结构（保持 <200 行）

参见 `assets/skill_template.md` 获取完整骨架。核心区块：

1. **核心角色** — 一句话
2. **适用场景** — 何时用/何时不用（快速判断）
3. **架构模式总览** — 一个表格
4. **创建流程概要** — 每步一句 + 指向详细文档
5. **参考资源** — 列出所有文件及何时读取

### C.3 写作原则

- 用祈使/不定式（"执行 X"而非"你应该执行 X"）
- 解释"为什么"让模型能判断边缘情况
- 步骤框架从 SKILL.md 分离，避免上下文膨胀
- 每个步骤描述只用 2-3 句话：目标 + 输入 + 输出

## Step D: 撰写步骤框架文件

每个 `references/step_frameworks/stepN_xxx.md` 遵循 `assets/step_framework_template.md`。

### 必须包含的三个部分

**1. 校验规则**（前置 + 后置 checklist）
- 前置：验证前一步骤完成标记存在、必要数据可用
- 后置：验证本步骤产出完整

**2. 核心执行流程**（具体操作命令）
- 每步操作给出明确的工具调用方式（Bash/Read/Edit）
- 不写"参考命令"这种模糊指导，写可直接复制执行的命令
- 命令中的占位符用 `{参数名}` 标注

**3. 完成标准与验收**
- 明确的 DONE 条件
- 失败处理指引（什么情况下需要人工介入）

### 关键约束

- 路径一致性声明在每个 step framework 开头都要有
- 每个步骤开头加上 `⚠️ 路径一致性要求` 警告块
- 禁止在框架文件中写"参考命令"代替实际命令

---

## Step E: 撰写脚本和模板

### E.1 必建脚本

**路径生成脚本**：根据用户输入参数生成确定的进度文件路径。这是最关键的脚本 — 保证每次调用生成相同路径。

参考 `biz-vul-security/scripts/interface_name_simplify.py` 的设计：
- 接受关键参数（接口名、应用名、分支名）
- 生成确定性的文件名和路径
- 创建空进度文件
- 输出绝对路径供后续步骤使用

### E.2 可选脚本

识别以下信号决定是否需要额外脚本：
- 需要从结构化数据（CSV/JSON）中匹配/查找 → 写匹配脚本（参考 `tr_interface_matcher.py`）
- 需要格式转换 → 写转换脚本
- 需要数据校验/清洗 → 写校验脚本

### E.3 模板文件

- `assets/progress_template.md`：定义进度文件的结构骨架
- `assets/output_template.md`：定义最终输出的格式（如有标准化输出）

## Step F: 迭代优化

Skill 创建不是一次性工作。用真实场景测试后，根据执行表现调整。

### F.1 测试方法

1. 准备 2-3 个真实输入（不同于 Step A.0 收集的示例，避免过拟合）
2. 用 skill 跑完全流程
3. 观察：哪些步骤模型执行流畅？哪些步骤出现跳步、遗漏校验、输出不完整？

### F.2 常见调整

| 观察到的现象 | 可能原因 | 调整方向 |
|-------------|---------|---------|
| 模型跳过 STEP 3 直接做 STEP 4 | 前置校验条件不够明确 | 在 STEP 3 和 STEP 4 的框架文件中强化前置依赖声明 |
| 进度文件中某个 STEP 的输出格式不一致 | 记录格式模板模糊 | 在步骤框架的"记录格式"部分给出更具体的模板 |
| 某步骤反复重新搜索相同内容 | 缺少缓存或进度记录 | 在步骤框架中增加"先检查进度文件中是否已有"的前置步骤 |
| 模型在可选步骤上花费大量时间 | 缺少决策分支 | 增加 if/else 判断条件和跳过标准 |
| 最终输出遗漏关键字段 | 输出模板不完整 | 对照真实需求补充模板中的必填项 |

### F.3 迭代节奏

- **第一轮**：跑 2-3 个真实案例，重点关注"步骤是否按顺序执行"和"最终输出是否完整"
- **第二轮**：关注效率和冗余 — 是否有步骤可以合并？是否有重复搜索？
- **稳定后**：只在使用中遇到新问题时再调整，避免过度优化

### F.4 何时考虑重写而非修补

如果出现以下情况，考虑重新设计：
- 修补超过 3 轮仍有同样的问题反复出现
- 步骤数膨胀超过 8 步（应拆分为多个 skill）
- 进度文件结构需要大改（说明最初的状态设计有误）
