# 六大架构模式 — 深度解析

本文档深入解析从 `biz-vul-security` 提取的六大架构模式，说明每个模式解决什么问题、如何实现、以及常见反模式。

---

## 模式 1: 进度文件驱动

### 解决的问题
多步骤任务中，模型容易丢失前几步的分析结果。没有统一的状态存储，步骤之间的信息传递依赖于模型的"记忆"，token 压缩后丢失。

### 实现方式
- 一个 Markdown 格式的进度文件贯穿全流程
- Step 1 通过脚本创建文件（确保路径确定性）
- 每个后续步骤从"读取"进度文件开始，"追加"新内容结束
- 使用 `=== STEP: STEP [n] - [名称] (开始/完成时间) ===` 作为步骤分隔标记

### 为什么用脚本生成路径而不是硬编码
- 相同输入必须生成相同路径，确保跨会话可恢复
- 路径规则改变时只需修改脚本，不涉及其它文件
- 文件名包含关键元数据（应用名、分支名、接口名），人类可读

### 反模式
- 每步生成新的临时文件（分散状态，无法追溯全流程）
- 用模型记忆代替文件记录（token 压缩后信息丢失）
- 路径手工拼接（不同次调用可能生成不同路径）

## 模式 2: 步骤框架分离

### 解决的问题
SKILL.md 如果包含每个步骤的完整操作细节，会轻松突破 500 行，导致：
- 每次都加载大量上下文，浪费 token
- 修改单步影响整个文件，难以维护
- 模型在不需要的步骤细节中"迷路"

### 实现方式
- SKILL.md 保持 <200 行，只写概览 + 每步一句话目标 + 资源索引
- 每个步骤的详细操作指南放在 `references/step_frameworks/stepN_xxx.md`
- 模型执行某步骤时才 Read 对应的框架文件
- 框架文件之间相互独立，修改一步不影响其他

### 分层示意
```
SKILL.md (始终在上下文，<200行)
  ├── Step 1 概要 (3行) → references/step_frameworks/step1.md (按需加载)
  ├── Step 2 概要 (3行) → references/step_frameworks/step2.md (按需加载)
  └── ...
```

### 反模式
- SKILL.md 包含完整操作命令（超过 500 行）
- 框架文件之间互相引用造成循环依赖
- 框架文件只写"参考命令"而没有具体可执行命令

## 模式 3: 三阶段执行

### 解决的问题
模型容易跳步、漏掉校验、或在没有完成前置步骤的情况下执行后续步骤。

### 实现方式
每个步骤必须严格遵循三阶段：

**阶段 1 — 前置校验**：
1. Read 进度文件末尾，验证前置步骤完成标记存在
2. Edit 追加本步骤开始标记

**阶段 2 — 执行与记录**：
1. Edit 追加命令记录（`**执行命令**: python3 ...`）
2. Bash 执行实际命令
3. Edit 追加分析结论

**阶段 3 — 后置校验**：
1. Read 进度文件末尾，验证本步骤关键产出已写入
2. Edit 追加本步骤完成标记

### 为什么这个顺序重要
- 前置校验用 Read 而非假设 — 如果前置步骤没完成，这里会发现
- 命令记录在前、执行在后 — 即使命令失败，进度文件也记录了尝试
- 后置校验用 Read 再验证 — 确保写入确实成功了

### 反模式
- 跳过前置校验直接执行
- 执行完后不验证就标记完成
- 用"参考命令"代替实际命令执行

## 模式 4: 脚本自动化

### 解决的问题
有些任务每次都要做，但不适合写在 SKILL.md 里（太细节），也不适合让模型每次自由发挥（结果不一致）。

### 什么适合写成脚本
- **路径生成**：根据参数生成确定性的文件路径
- **数据匹配**：在结构化数据中查找模式（如 CSV、JSON）
- **格式转换**：将一种格式转为另一种
- **数据校验**：检查输入/输出的完整性

### 什么不适合写成脚本
- 需要理解语义的分析任务（如"判断这个校验是否充分"）
- 一次性使用的临时脚本
- 过于简单的单行命令（如 `cat file1 file2 > file3`）

### 脚本设计原则
- 输入输出明确（CLI 参数 或 stdin/stdout）
- 独立的，不依赖其他脚本的运行时状态
- 有 `--help` 和错误处理
- 通过绝对路径调用（`python3 ~/.claude/skills/{skill}/scripts/xxx.py`）

### 反模式
- 脚本承担了应该由模型完成的语义判断
- 脚本之间强耦合
- 脚本路径硬编码

## 模式 5: 资源分层

### 解决的问题
Skill 的资源（参考文档、模板、数据、规则）如果全部放在 SKILL.md 中，会严重膨胀上下文。需要按使用频率分层加载。

### 四级加载模型

| 层级 | 位置 | 何时加载 | 大小限制 |
|------|------|---------|---------|
| **L1 元数据** | Frontmatter name + description | 始终 | ~100 字 |
| **L2 主体** | SKILL.md body | skill 触发时 | <200 行 |
| **L3 步骤框架** | `references/step_frameworks/` | 执行对应步骤时 Read | <100 行/文件 |
| **L4 参考/模板** | `references/` + `assets/` | 需要时 Read | 无硬限制 |

### 设计要点
- L2 (SKILL.md) 必须能独立回答"这个 skill 做什么、有哪些步骤"
- L3 (框架文件) 必须包含足够详细的可执行命令
- L4 (参考/模板) 只在特定步骤中需要才 Read

### 反模式
- 把所有内容堆在 SKILL.md 中
- 框架文件中引用模板内容（应该引用文件路径，让模型自己 Read）
- references 文件没有在 SKILL.md 中说明"何时读"

## 模式 6: 路径一致性

### 解决的问题
多步骤中，每个步骤都可能生成临时文件。如果路径规则不统一，后续步骤找不到前面步骤的产出。

### 实现方式
- Step 1 通过脚本生成唯一的 `{progress_file_path}`
- 所有后续步骤使用占位符 `{progress_file_path}` 引用此路径
- 每个步骤框架文件开头有 `⚠️ 路径一致性要求` 警告块
- 禁止步骤重新生成路径或使用不同的命名规则

### 为什么用占位符而不是直接写路径
- 路径在 Step 1 才确定，框架文件中不能硬编码
- 占位符提醒模型"这个值需要替换"，减少出错
- 人类 review 时能清楚看到哪些地方依赖共享路径

### 反模式
- 每个步骤独立生成文件路径
- 步骤间用了不同的路径约定
- 框架文件中硬编码了示例路径
